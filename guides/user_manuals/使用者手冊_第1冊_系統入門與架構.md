## 🎯 系統概述

**AIVA (AI-Driven Vulnerability Assessment)** 是一個企業級 Bug Bounty 平台，採用 AI 驅動的智能決策系統，專精於：

- ✅ **動態漏洞檢測** - 自動化黑盒滲透測試
- ✅ **智能攻擊策略** - AI 驅動的決策引擎
- ✅ **多語言協同** - Python/Rust/Go/TypeScript 引擎
- ✅ **Bug Bounty 優化** - 針對 HackerOne/Bugcrowd 實戰場景

### 核心特性

| 特性 | 說明 |
|------|------|
| 🧠 **AI 決策引擎** | 5M 參數神經網路 + RAG 向量檢索 |
| 🎯 **四大決策方法** | 掃描策略、Phase1/2 決策、結果評估 |
| 🔍 **多引擎掃描** | Python/Go/Rust/TypeScript 協同 |
| 📊 **企業級標準** | CVSS v3.1、MITRE ATT&CK、SARIF v2.1.0 |
| 🔄 **雙閉環學習** | 內閉環 (即時) + 外閉環 (經驗學習) |

## �️ 黑盒測試策略

### 核心理念

AIVA 採用**黑盒測試**方法，意味著系統在完全不了解目標內部情況下進行滲透測試：

```
黑盒測試 = 零知識前提 + 多路並行探查
```

**面臨的挑戰**：
- ❓ 不知道開了哪些端口
- ❓ 不知道使用什麼技術棧
- ❓ 不知道有沒有 WAF
- ❓ 不知道目錄結構
- ❓ 不知道 API 端點

### 多路並行探查策略

為了克服信息不足的問題，AIVA 在 Phase 0 規劃階段會同時派出多個獨立的探查任務：

```
                    目標網站
                       ↓
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
   探查任務 1      探查任務 2      探查任務 3
   (HTTP 探測)    (端口掃描)      (WAF 檢測)
        ↓              ↓              ↓
        └──────────────┼──────────────┘
                       ↓
              整合所有結果
                       ↓
                  AI 決策
```

**典型的 5 路並行探查**：

| 任務 | 工具 | 目的 | 耗時 |
|------|------|------|------|
| HTTP 基礎探測 | httpx | 確認服務可達性、獲取 headers | ~3s |
| 端口掃描 | port_scanner | 發現開放端口、服務類型 | ~5s |
| WAF 檢測 | waf_detector | 判斷是否有防火牆 | ~2s |
| 技術棧指紋 | tech_stack | 識別框架、語言、數據庫 | ~3s |
| 目錄發現 | directory_scanner | 發現隱藏目錄和 API | ~10s |

**並行執行優勢**：
- ⏱️ **節省時間**: 5 個任務並行只需 10 秒（最長任務時間），順序執行需 23 秒
- 🛡️ **容錯性**: 即使某個探查失敗，其他探查仍可提供情報
- 🔗 **互補性**: 不同角度的探查結果互相驗證和補充

### Rust 引擎的角色

**為什麼需要 Rust？**

Python 受限於 GIL（全局解釋器鎖），無法實現真正的多線程並行。Rust 引擎負責高性能的並行任務執行：

```python
# Python: 受限於 GIL
async def slow_scan():
    tasks = [scan1(), scan2(), scan3()]
    results = await asyncio.gather(*tasks)
    # 仍然是 I/O 並發，不是真正的並行

# Rust: 真正的多線程並行
fn fast_scan() {
    let tasks: Vec<_> = (0..100)
        .map(|i| tokio::spawn(scan_task(i)))
        .collect();
    // 真正的多線程並行執行
}
```

**性能對比**：
- Python asyncio: 100 個任務 ≈ 30 秒
- Rust tokio: 100 個任務 ≈ 5 秒
- **效能提升**: 6 倍

### 規劃與執行分離原則

AIVA 嚴格遵循「規劃與執行分離」原則：

```
步驟 N 的輸出 → 步驟 N+1 的輸入依據
```

**核心流程**：

| 步驟 | 職責 | 為什麼重要 |
|------|------|-----------|
| **Step 3: 規劃** | 決定要探查什麼 | 根據目標特性制定策略 |
| **Step 4: 執行** | 實際執行探查 | 高性能並行執行（Rust） |
| **Step 5: 整合** | 合併所有結果 | 提供完整情報給 AI |
| **Step 6: 決策** | AI 分析並決策 | 基於完整資訊做智能判斷 |

**為什麼不能合併？**
- ❌ 邊規劃邊執行 → 無法並行，浪費時間
- ❌ 單一探查 → 資訊不足，決策失誤
- ✅ 先規劃後執行 → 5+ 路並行，完整情報

詳細的代碼實現、實戰案例和性能對比，請參見 **[第 2-2 冊：13 步驟黑盒測試架構詳解](使用者手冊_第2-2冊_13步驟黑盒測試架構詳解.md)**。

## �🚪 程式入口點

AIVA 採用**單一入口架構**，直接執行 `app.py` 即可啟動完整系統：

### 🚀 app.py - 系統唯一入口 (Port 8000)

**位置**: `services/core/aiva_core/service_backbone/api/app.py`  
**角色**: AIVA 系統的唯一入口點，整合 AI 決策引擎和掃描執行

**職責**:
- ✅ 接收掃描請求（HTTP API 或 CLI）
- ✅ 調用 AI 決策引擎
- ✅ 協調任務規劃與執行
- ✅ 雙路分離處理（實時記錄 + AI 決策）
- ✅ **啟動時自動初始化所有執行器**

**啟動方式**:
```bash
# 方式 1: HTTP 服務模式（推薦）
python services\core\aiva_core\service_backbone\api\app.py
# 服務運行在 http://0.0.0.0:8000

# 方式 2: CLI 直接掃描模式
python services\core\aiva_core\service_backbone\api\app.py --target http://localhost:3000

# 可選參數
python services\core\aiva_core\service_backbone\api\app.py --port 8000 --host 0.0.0.0
```

**API 端點**:
- `GET /health` - 健康檢查
- `GET /docs` - API 文檔（Swagger UI）
- `POST /scan` - 創建掃描任務
- `GET /status/{scan_id}` - 查詢掃描狀態

**啟動流程與依賴注入**:
```python
# app.py 的 startup() 函數執行順序
1. 創建 UnifiedAttackExecutor
2. 創建 MultiEngineCoordinator  
3. 創建 InternalLoopConnector
4. 將這些執行器注入到 CommanderCoordinator
5. CommanderCoordinator 再將執行器傳遞給 AttackCoordinator

# 依賴注入模式（從外向內）:
app.py (startup)
    → 創建 unified_executor
    → 創建 multilang_coordinator  
    → 創建 internal_loop
    → CommanderCoordinator(unified_executor, multilang_coordinator, internal_loop)
        → AttackCoordinator(unified_executor, multilang_coordinator, internal_loop)
```

**數據流**:
```
外部請求（HTTP API 或 CLI）
    ↓
app.py (Port 8000) - 系統唯一入口
    ↓
雙路分離處理:
  ├─ 路徑1: integration 模組存儲（實時記錄）
  └─ 路徑2: AI 決策 → 任務規劃 → 執行模組
```

> **💡 架構簡化說明 (v4.4.1)**:
> - 移除 main.py (Port 9000) 安全網關層
> - app.py 直接作為唯一入口，簡化部署
> - 支援 CLI 掃描模式：`--target URL`

## 📝 附錄

### A. 常見問題 (FAQ)

**Q1: 為什麼需要兩個入口點（main.py 和 app.py）？**

A: 這是安全設計。`main.py` 作為第一道防線，過濾惡意請求後才轉發給 `app.py`（AI 系統），避免 AI 系統受到污染或攻擊。

**Q2: 可以只啟動 app.py 嗎？**

A: 可以，但不建議。生產環境應該使用 `main.py` 作為對外入口，確保安全性。開發測試時可以直接訪問 `app.py` (Port 8000)。

**Q3: 如何查看詳細日誌？**

A: 日誌位於 `logs/` 目錄，或使用 `docker-compose logs -f` 查看即時日誌。

**Q4: 系統支援哪些掃描類型？**

A: 支援 `quick`（快速掃描）、`full`（完整掃描）、`deep`（深度掃描）、`custom`（自定義掃描）。

**Q5: 如果只想使用基本掃描功能，最少需要安裝哪些依賴？**

A: 最少需要 Python 3.11+ 和 7 個核心套件：
```bash
pip install fastapi uvicorn httpx pydantic requests beautifulsoup4 lxml
```
安裝後執行：
```bash
python -c "import fastapi, uvicorn, httpx, pydantic, requests, bs4; print('✅ 核心依賴已就緒')"
```

**Q6: 數據流分析功能需要安裝 Go/Rust/Node.js 嗎？**

A: 視情況而定：
- **內部分析**（171 個 Python flows）：只需 Python 標準庫（ast, json, pathlib），無需額外安裝
- **外部分析**（525 個 flows）：僅當需要分析特定語言的外部模組時才安裝對應編譯器：
  - Go 模組（2 個 flows）：需要 Go 1.21+
  - Rust 模組（2 個 flows）：需要 Rust 1.75+ + Cargo
  - TypeScript 模組（0 個 flows）：需要 Node.js 20+ + npm + ts-node
- **執行器功能**：已有預編譯產物（go2mermaid.exe、rs2mermaid.exe），不需要額外安裝編譯器即可執行

**Q7: 如何驗證所有依賴已正確安裝？**

A: 執行環境驗證腳本（詳見 §2.3.2 數據流分析環境驗證）：
```bash
# 1. 檢查 Python 版本（需要 3.11+）
python --version

# 2. 檢查核心依賴
python -c "import fastapi, uvicorn, httpx, pydantic, requests, bs4; print('✅ 核心依賴已就緒')"

# 3. 檢查內部分析依賴（Python 標準庫）
python -c "import ast, json, pathlib, asyncio, importlib; print('✅ 標準庫可用')"

# 4. 測試內部分析器
python services/integration/data/internal_exploration/analyzer.py

# 5. 測試外部執行器
python services/integration/data/internal_exploration/executor.py
```

**Q8: 安裝依賴時遇到錯誤怎麼辦？**

A: 常見問題與解決方案：
- **pip 版本過舊**：執行 `python -m pip install --upgrade pip`
- **權限問題**：使用 `--user` 參數：`pip install --user <package>`
- **網路問題**：使用國內鏡像源：`pip install -i https://pypi.tuna.tsinghua.edu.cn/simple <package>`
- **編譯錯誤**（如 lxml）：安裝預編譯版本：`pip install --only-binary :all: lxml`
