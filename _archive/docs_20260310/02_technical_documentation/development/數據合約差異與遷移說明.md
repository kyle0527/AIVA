## 一、核心差異(簡單版）

### 問題：你提出的需求

**你的需求**（AI 自動化閉環完整實施計劃.md）:

### 解決方案：新增 Core ↔ Features 調用合約

#### 新版數據合約（用於 Core → Features）

**位置**: `services/aiva_common/schemas/feature_schemas.py`（待創建）

```python
class FeatureRequest(BaseModel):
    """Core 發給 Features 的請求（輕量級）"""
    feature_type: FeatureType       # XSS, SQLI, SSRF...
    target: HttpUrl                 # http://target.com
    options: Dict[str, Any] = {}    # {"timeout": 30, "depth": 2}
    
    # 優化參數（從反饋循環獲得）
    concurrency: Optional[int] = None
    preferred_payloads: Optional[List[str]] = None

class FeatureResult(BaseModel):
    """Features 返回給 Core 的結果（輕量級）"""
    success: bool                   # True/False
    feature_type: FeatureType       # XSS
    target: str                     # http://target.com
    vulnerabilities: List[Vulnerability]  # 簡化的漏洞列表
    metadata: Dict[str, Any]        # 基本統計
    error: Optional[str] = None     # 錯誤信息
```

**特點**：
- ✅ 輕量級（Core 只需要知道成功/失敗和漏洞數量）
- ✅ 標準化（所有 Features 統一格式）
- ✅ 可擴展（支持優化參數傳遞）

## 三、為什麼需要兩套？

### 場景 1：Core 調用 Features（需要輕量級）

```python
# AICommanderV2 只需要知道：
# 1. 調用成功了嗎？
# 2. 發現了幾個漏洞？
# 3. 需要繼續測試嗎？

result = await features_invoker.invoke_feature(
    FeatureRequest(
        feature_type=FeatureType.XSS,
        target="http://target.com"
    )
)

if result.success and len(result.vulnerabilities) > 0:
    print(f"✅ 發現 {len(result.vulnerabilities)} 個 XSS 漏洞")
    # 決定下一步行動
```

**需求**：快速、輕量、標準化

---

### 場景 2：Coordinator 分析雙閉環（需要詳細版）

```python
# XSSCoordinator 需要：

internal_result: FeatureResult = await func_xss.scan(...)

    internal_result.findings  # 需要完整 Finding 對象
)

    internal_result.findings  # 需要證據和元數據
```

**需求**：詳細、完整、可分析

## 四、遷移策略要解決什麼？

### 問題：兩套格式如何共存？

**不遷移的後果**：
```python
# ❌ 命名衝突
from aiva_common.schemas import FeatureResult  # 新版
from services.features.base import FeatureResult  # 現有
# 💥 衝突！哪個是哪個？

# ❌ 類型混亂
def process_result(result: FeatureResult):  # 這是哪個版本？
    # Core 傳入新版，Coordinator 期望舊版 💥
```

---

### 解決方案：分層隔離 + 自動轉換

#### 策略 1：命名空間隔離

```python
# Core 層（使用新版）
from aiva_common.schemas.feature_schemas import (
    FeatureRequest,
    FeatureResult as CoreFeatureResult
)

# Features 層（使用現有）
from services.features.base import (
    FeatureResult as InternalFeatureResult
)

# Coordinator 層（使用現有）
from services.integration.coordinators.base_coordinator import (
    FeatureResult  # 擴展版
)
```

**結果**：各層使用自己的格式，無衝突。

---

#### 策略 2：FeaturesInvoker 做自動轉換

```python
class FeaturesInvoker:
    """統一調用接口，負責格式轉換"""
    
    async def invoke_feature(
        self,
        request: FeatureRequest  # Core 傳入新版
    ) -> CoreFeatureResult:      # Core 接收新版
        
        # 1. 調用 Features（內部使用舊版）
        internal_result: InternalFeatureResult = await func_xss.scan(
            target=str(request.target),
            options=request.options
        )
        
        # 2. 轉換為新版輕量級格式
        core_result = CoreFeatureResult(
            success=(internal_result.status == "SUCCESS"),
            feature_type=request.feature_type,
            target=str(request.target),
            vulnerabilities=[
                self._simplify_finding(f)
                for f in internal_result.findings
            ],
            metadata={
                "scan_duration": internal_result.execution_time,
                "vulnerabilities_count": len(internal_result.findings)
            }
        )
        
        # 3. 同時觸發 Coordinator 處理（使用完整格式）
        asyncio.create_task(
            self._trigger_coordinator(internal_result)  # 傳遞完整格式
        )
        
        return core_result
    
    def _simplify_finding(self, finding: Finding) -> Vulnerability:
        """將完整 Finding 轉換為簡化 Vulnerability"""
        return Vulnerability(
            type=finding.vulnerability_type,
            location=finding.affected_url,
            severity=finding.severity,
            confidence=finding.confidence.value
        )
```

**結果**：
- ✅ Core 收到輕量級結果（快速決策）
- ✅ Coordinator 收到完整結果（深度分析）
- ✅ Features 內部不需要修改

## 六、總結：一句話說明

### 核心差異

**現有**: Features 內部用的詳細格式（給 Coordinator 分析）  
**新版**: Core 調用 Features 用的輕量格式（快速傳輸）

### 為什麼需要遷移策略

**不是真的"遷移"**，而是**共存策略**：
- Core 用新版（輕量級，快速決策）
- Features 用舊版（詳細版，深度分析）
- FeaturesInvoker 做橋接（自動轉換）

### 比喻說明

```
新版 = 電報（簡短、快速）
  "發現3個XSS漏洞，繼續測試" 
  ↓
  用於：AI 快速決策下一步

舊版 = 完整報告（詳細、全面）
  "漏洞詳情、證據鏈、優化建議..." 
  ↓
  用於：深度分析和報告生成
```

**兩者都需要**，各有用途，不是替換關係。

---

## 七、你需要知道的關鍵點

1. **不會破壞現有功能** ✅
   - Features 內部不需要修改
   - Coordinator 繼續使用現有格式

2. **實現 AI 自動化閉環** ✅
   - Core 可以標準化調用所有 Features
   - 一個指令自動完成所有步驟

3. **保持雙閉環完整** ✅
   - 內循環/外循環分析不受影響
   - FeaturesInvoker 會自動觸發 Coordinator

4. **工作量小** ✅
   - 3.5-4.5 天完成
   - 主要是新增代碼，不是修改現有代碼

---

**結論**: 遷移策略不是"換掉舊的"，而是"新增一個輕量級接口層"，讓 AI 可以自動調用 Features，同時保持現有的深度分析功能完整。
